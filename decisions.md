# Decisions Log

Use this template for every consequential design decision.

- KL direction: log_ratio = ref_logps - current_logps, so s = π_ref/π_θ.
- Importance ratio direction: exp(current_logps - old_logps), so ratio = π_current/π_old.
- Std: population, chosen because matches DeepSeekMath.
- Zero-variance handling: divide by (std + eps).
- Pooled global mean: longer completions get proportionally more gradient influence; accepted deliberately since amplifying the penalty on long, wrong completions is desirable for a math-reasoning model, not just a side effect to tolerate
- `ppo_epochs=1` (default, configurable). Old and current policy are the same weights at the only gradient step this batch, so `ratio ≈ 1` and `clip_range` doesn't engage yet — deliberate, to keep Phase 2 debugging to one axis at a time.
- Reference policy fixed for the entire run — implemented via `model.disable_adapter()` on the same LoRA-wrapped model rather than a separate frozen model copy, since the base weights never change and LoRA is zero-initialized. No duplicate model in memory.
- Checkpointing every `save_steps` (config, defaults to `max_steps` i.e. final-only if unset) plus always on the last step.
- Rig baseline: pipeline verified working on RTX 3060 Ti via CUDA_VISIBLE_DEVICES=1,2,3.
- GPU 0 reserved for display: NVIDIA's Linux driver enforces a watchdog timer on any GPU actively driving an X session, killing long-running CUDA kernels. Not a config issue — GPU 0 can't be used for training while it's also driving the desktop, short of disabling the display manager entirely (declined, since remote desktop access is still needed sometimes).
- Only 4 GPUs consistently detected via nvidia-smi throughout, despite the design doc's original 5-GPU assumption. No 5th card ever found; treating actual hardware as 4x RTX 3060 Ti going forward.
- Dev run config (Qwen 0.5B, 25 steps): pipeline verified, expected zero-reward pattern for undertrained small model.
- policy_loss diagnostic unreliable at group_size=2 due to advantage symmetry and pooled global mean. KL and reward are more informative for detecting learning at this scale. Address if we want reliable diagnostics at small group sizes later.
- Qwen 2.5-1.5B on RTX 3060 Ti (8GB VRAM) with LoRA rank 8:
  - group_size=4 OOMs at current_logps forward pass (7.47 GiB used of 7.79 GiB)
  - group_size=2 works
  - The forward pass for current_logps is the memory bottleneck (only pass retaining gradients)
  - Increasing group_size would require: lower per_device_batch_size, gradient checkpointing, or shorter max_new_tokens
- clip_fraction bug: original check compared L_clip to clip_ratio*advantages alone, which is trivially true whenever ratio is already inside the clip band (both candidates equal by construction) — inflated to 1.000 on every run regardless of real clipping. Fixed by requiring both the equality AND ratio actually outside [1-clip_range, 1+clip_range].
- Diagnostics detach bug: policy_loss/kl in grpo_loss's returned dict retained the full autograd graph (missing .detach()), contradicting the function's own "detached diagnostics" contract. Harmless today since train.py only ever calls .item() on them, but would silently leak memory if metrics were ever accumulated across steps without detaching first. Fixed.
- modeling.py device bug: load_policy picked bfloat16 dtype based on cuda availability but never called .to(device) — model would have silently trained on CPU even with GPUs present. Fixed with explicit .to(device).
- Rig-specific: transformers appears to default to compiled generation on CUDA but not MPS (Mac ran fine on an even newer transformers version; rig stalled indefinitely with 8 torch._inductor compile workers and zero progress). Fixed by exporting TORCHDYNAMO_DISABLE=1. Root cause (which specific transformers setting triggers this) not fully identified — the env var is a blunt but effective workaround.
- Hardware incident: GPU 1 threw Xid 79 ("GPU has fallen off the bus") on its first sustained compute load; a warm reboot did not recover it, a full physical power cycle did. Likely a marginal riser/power connection given this is a riser-based multi-GPU rig — reseat GPU 1's riser and power cable if it recurs.
- Training-reward curves are confounded with problem sampling, not a reliable "is the model learning" signal on their own: with max_train_examples=1000 and only ~200 prompt draws over a 100-step run, no training example repeats within a run, so a rise in mean reward (e.g. first-half vs second-half) can't be distinguished from that half's problems happening to be easier. Real learning-progress questions need evaluate.py comparing the same fixed held-out test set across checkpoints, not the training log.
- max_new_tokens=128 was very likely too low: every completion in the compare_checkpoints run (base + all 5 checkpoints) landed at ~126-127/128 tokens regardless of correctness, strong evidence of systematic truncation before reaching \boxed{}. This affected training rollouts, not just eval, and is a plausible root cause for the weak/flat reward signal throughout full_run. Bumped to 512 as a cheaper first fix before escalating to 1024.
- Gradient checkpointing enabled on the trainable policy (not on load_base_model, which evaluate.py also uses with no backward pass to benefit from it). Requires model.enable_input_require_grads() alongside gradient_checkpointing_enable() specifically because the base model is frozen — otherwise checkpointing has no requires_grad=True input to recompute from during backward.
- Multi-GPU data parallelism added via accelerate (Accelerator, prepare(), accelerator.backward()), targeting the 3 non-display GPUs. per_device_batch_size now means what its name says — total prompts per step scale with num_processes. Each process gets a disjoint data slice via a process-index-offset cursor with a num_processes-sized stride. Generation and disable_adapter() run on the unwrapped model; checkpoint saving is main-process-only after an explicit wait_for_everyone() barrier. Verified only in single-process mode (no multi-GPU environment available to test against) — the actual multi-process path is unverified until run on the rig.
- Bug found in the first real 3-GPU full_run: checkpoint-40/60/80/100 were byte-identical (confirmed via md5sum) despite the training log showing genuinely varying, non-zero policy_loss/kl throughout — the model silently stopped actually updating partway through while forward-pass loss values kept looking normal. Root cause: gradient checkpointing + DDP is a known problematic combination — activation recomputation during backward can confuse DDP's default gradient-sync hook ordering, and its bucket-rebuild heuristic can silently lock onto a broken sync configuration a few iterations in. Fixed with `DistributedDataParallelKwargs(static_graph=True)` passed to `Accelerator(kwargs_handlers=[...])`. All full_run checkpoints from this run should be treated as unreliable (at minimum 40 onward frozen; 20 unverified) — needs a clean retrain with the fix in place.
